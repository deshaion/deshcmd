# Deshcmd filesystem navigation performance plan

**First priority — shorten the path to a usable first screen.** Today a new directory shows zero entries until the last entry has metadata and the UI has sorted and filtered the entire result. Start with the existing engine and virtualized views. Make directory work discardable, produce a small usable page early, and move whole-list preparation off the input thread. A watcher and speculative prefetch are later projects. Neither helps the first cold visit to an unfamiliar directory.

## A. Architecture assessment

Reviewed workspace revision `cc30d40`. The engine uses synchronous Rust filesystem APIs on ordinary threads and sends events through standard-library channels. The desktop currently uses eframe/egui 0.37 and wgpu. Linux/X11 is the verified desktop in the README. The design below keeps native platform integration in the launcher and the listing protocol usable in headless tests. [Workspace manifest](../Cargo.toml) · [Platform scope](../README.md)

### Confirmed work outside enumeration

- **Sort and filter.** `sort` compares lowercased strings allocated by `compare_names` on each name comparison, including fallback ordering. The natural comparator scans digit runs, including leading zeros. Each inline edit in `tools` dispatches Filter. `matching` compiles a mask when applicable, normalizes names even for an empty query and collects matching references. `filter_entries` builds a path hash set from these, scans again to produce visible indices and prunes marks/cursor. Recursive filtering also collects excluded directories and checks ancestors. Sort clicks call `resort` then filter again. Changing global sort preferences in `save_settings` dispatches Refresh, causing filesystem work. Hidden/ignore changes refilter only the two active tabs, so an inactive tab can show an old projection on return. [Ordering and matching](../crates/deshcmd-engine/src/listing.rs) · [Engine commands](../crates/deshcmd-engine/src/lib.rs) · [Settings](../crates/deshcmd-ui/src/settings.rs)
- **Selection and frame cost.** `App::footer` builds `operands()` merely to enable buttons. With marks this scans all entries and clones every marked path each time the footer draws. Without marks it searches for the cursor. `panel_status` scans entries for selected bytes when marks exist. `current`, Step, range selection and scroll-to-cursor also search linearly. Visible rows build tooltip strings even when the pointer is elsewhere. `dialogs::invoke` eagerly materializes selected and marked paths before choosing most tools. Export Details with no marks clones every visible path, then calls linear `Vec::contains` for each row, a quadratic membership test. [Footer and Quick View](../crates/deshcmd-ui/src/lib.rs) · [Status and reveal](../crates/deshcmd-ui/src/panes.rs) · [Dialog actions](../crates/deshcmd-ui/src/dialogs.rs)
- **Other foreground filesystem calls.** `App::content` fills the space cache per base path with two fs2 calls. Failed values are retried on every draw. `App::logic` clears that cache and synchronously enumerates places every ten seconds, with a one-second repaint timer. `App::new` also enumerates places. Linux reads mountinfo, macOS enumerates volumes and Windows probes drive letters. Expanded `panes::tree` nodes call `tree_folders` on a five-second cache miss, enumerate and sort all children before taking 250, and retrieve an owned folder vector even on cache hits. Startup validates CLI directories before creating the window. Dialogs read lists, inspect properties/numbered parts and validate destinations synchronously on demand. These paths matter even with a fast main scan. [UI lifecycle](../crates/deshcmd-ui/src/lib.rs) · [Tree](../crates/deshcmd-ui/src/panes.rs) · [Native adapter](../apps/deshcmd-desktop/src/main.rs) · [Dialog I/O](../crates/deshcmd-ui/src/dialogs.rs)
- **Refresh and memory.** Each tab retains its own current entries, visible indices, marks and history. History stores locations, including owned path lists for virtual locations. Returning through history starts another scan. There is no shared directory snapshot or native filesystem watcher. `poll` dirties each active nonrecursive, non-flat tab every four seconds with auto-refresh enabled, including List tabs. A slow scan can become dirty before it completes and start another immediately. Manual Refresh and every job Done dirty all tabs, including after read-only jobs. Inactive dirty tabs defer work until activation. The transient path vector, dedup set, per-parent comment maps, old/new listings on refresh and matching structures can overlap in memory. [Tab storage and refresh policy](../crates/deshcmd-engine/src/lib.rs) · [Scan allocations](../crates/deshcmd-engine/src/listing.rs)
- **Concurrency boundaries.** Engine events use an unbounded channel drained to exhaustion. Job execution is intentionally serialized, progress reports are throttled to roughly one per 60 ms, and `Control` supports pause, cancel and conflict resolution. `Drop for Engine` cancels jobs. Listing threads have no cancellation hook or shared concurrency cap. Closing tabs or restoring a workspace can strand work until completion. Preview has a separate worker, a nonblocking 32-slot request FIFO, pending-key deduplication and a 150-item insertion-order cache keyed by path, mtime and pixel size. Decode limits and a 24 KiB text cap already exist. Results use an unbounded channel and `Previews::poll` uploads all arrived images that pass through it. Fast scrolling can leave obsolete previews ahead of the current one. Queue capacity, texture bytes and peak decoder bytes are distinct limits. [Engine](../crates/deshcmd-engine/src/lib.rs) · [Job control and reporting](../crates/deshcmd-engine/src/operations.rs) · [Preview queues](../crates/deshcmd-ui/src/lib.rs) · [Decoder limits](../crates/deshcmd-engine/src/listing.rs)

### Evidence and open questions

A temporary headless probe exercised the public engine API at the reviewed revision. Release build, rustc 1.96.0, Linux x86-64, local ext4. Create 100,000 empty files named `file0.txt` through `file99999.txt` and a separate empty directory. Start both panes in the empty directory with default settings except auto-refresh disabled. Wait for both initial scans, dispatch Navigate in the left pane to the large directory, wait on the engine wake callback and time each poll until loading clears. Assert exactly 100,000 visible entries. Return to the empty directory between trials. File creation precedes timing, OS caches are warm/uncontrolled, and there is no GUI, selection, tree or preview.

| Milliseconds, in run order | 1 | 2 | 3 | 4 | 5 | Median |
|---|---:|---:|---:|---:|---:|---:|
| Dispatch start to complete visible model | 471.5 | 463.1 | 460.1 | 456.3 | 464.0 | 463.1 |
| Longest poll during that navigation | 225.1 | 223.7 | 229.7 | 224.6 | 232.2 | 225.1 |

On this fixture the first available model is the final model. The longest poll includes installing, sorting and filtering the listing. The experiment does not isolate the cost of those stages or measure presentation latency. Five warm observations establish the scale of the current stall. Slow-mount first read, peak RSS, syscall counts, UI-thread destruction of old results, frame pacing, platform-specific metadata reuse and the value of speculation all require separate measurements.

### What to take from Yazi

Yazi's author describes loading directory contents in chunks, retaining directory state, discarding obsolete work, processing previews by visible page and merging render requests. Its merged large-directory change demonstrates the distinction between seeing results and finishing a scan. For Deshcmd the counterparts are an early page, a bounded revisioned snapshot, cooperative cancellation and a single repaint per delivery cycle. Keep both panes interactive and preserve the existing job conflict queue. The model needs no terminal renderer, plugin host or async runtime migration. [Yazi’s design account](https://yazi-rs.github.io/blog/why-is-yazi-fast/) · [Chunked directory loading change](https://github.com/sxyazi/yazi/pull/117)

## B. Optimization choices

Each row is a proposal. The expected benefits are hypotheses or reductions in a specific unit of work. Task numbers below define the release gates.

| Priority and intervention | Work removed or deferred, expected user effect | Complexity and main trade-off | Deciding measurement |
|---|---|---|---|
| P0 · Viewport and selection queries (2) | Replace marked-path materialization and repeated scans on draw with maintained counts and cursor position. Stable-frame cost should follow visible row count. | Low for footer, medium for selection invariants. Index/aggregate maintenance adds work when a view changes. | Entries visited, paths cloned and frame CPU with 0, 1 and 100k marks. |
| P0 · Bound and supersede scans (3) | Latest visible destinations get service before obsolete work. Cap live scans, queued requests and retained results. | Medium. An OS call already blocked on a mount can still occupy a slot. | Peak workers/queued bytes, abandoned entries processed and delay until the winning scan starts. |
| P0 · Resolve locations and sidebar data off-thread (4–5) | Keep input, spinner and the opposite pane responsive during path validation, volume probes and tree expansion. | Medium. Async results can target a different tab, dialog or volume by arrival time. | UI heartbeat during injected delays and real unavailable mounts, including first launch. |
| P0 · Prepare views off-thread (6–7) | Reuse enumeration metadata, avoid redundant path copies and per-comparison name folds. Publish a ready row order. Sort/filter changes need no I/O when scope is unchanged. | Medium. Cached keys and immutable generations increase peak bytes. Query revisions must be checked at commit. | Scan, sort, filter, install and drop timings separately, allocations per row, metadata calls and result parity. |
| P0 · Incremental initial display (8) | Make a bounded first page usable while enumeration continues. The user can leave before paying for the entire directory. | Medium. Early order is provisional. Frequent global resorting or unstable click targets would defeat the change. | First useful painted row, input latency during load, final order/time and number of whole-list sorts. |
| P1 · Share bounded snapshots and narrow invalidation (9–10) | Revisit and simultaneous-pane loads reuse data. An idle pane or read-only operation should generate little directory work. | Medium. Retention competes with active tabs for memory. Freshness varies by filesystem. | Revisit paint time, shared scan count, retained bytes, idle scans/minute, mutation-to-visible delay. |
| P1 · Watch and reconcile (11–12) | Change notifications replace routine full scans on supported active directories. Small edits update only affected entries. | Medium for invalidation, high for deltas. Overflow, rename ambiguity and network mounts require recovery. | Reads and sorts per single edit, convergence after a burst, idle and overflow scan counts. |
| P2 · On-demand enrichment and speculative work (13–14) | Limit metadata and decoding to what the active sort, filter, action and viewport require. Optionally warm a likely next directory. | High for lazy metadata, medium for previews, low incremental effort for prefetch after caching. Guesses can waste I/O. | Metadata/visible row, useful prefetch hits per byte, quick-view latency, peak decoded/texture bytes and foreground regression. |

## C. Implementation tasks and release gates

Use the following order within each dependency chain. Tasks 2, 3 and 6 can start independently after the baseline. Deliver through task 8 and remeasure before expanding scope. Each task should be a reviewable change. Module names below are relative to `crates/deshcmd-engine/src` (**engine**) or `crates/deshcmd-ui/src` (**UI**) unless identified as desktop. Reuse `crates/deshcmd-engine/tests/workflow.rs` for command-level behavior.

### 1. Capture a reproducible baseline — P0, no dependency

**Phase 1 status — baseline captured.** The release harness, fixture, stage timings, RSS, Linux syscall trace and delayed-reader ordering test are in place. [Results and reproduction](performance-phase1-results.md). Release measurements still pending include isolated cold-cache runs, a slow or remote mount, native presentation timing, and ordinary queue-depth high-water. The 100 ms first-usable-row and 16.7 ms large-install poll targets remain open.

Add a release-mode harness under the engine's benches or an ignored integration test, with optional timing hooks at `start_scans`, `scan`, `sort`, `filter_entries`, `poll`, and the UI's `logic`/first populated `rows` or `gallery` frame. Include an empty-to-empty reference. Timestamp request, worker start, first eligible entry, publication, UI install, first populated draw and final settled draw. Use a frame-present callback if available and otherwise label draw submission explicitly. Record queue depths, canceled work, batch bytes, metadata attempts and peak resident memory. Keep clocks/logging outside per-entry loops where possible.

**Acceptance and benchmark.** Reproduce the headless protocol above. Compare baseline/candidate on identical hardware and builds with 100, 10k and 100k+ entries, scrambled numeric names, directories, links, hidden files and comments. Exercise first visit, repeated A→B→A, both panes on one directory, recursive search, scroll, type-to-filter, mark all and navigation during a transfer. Include a deterministic delayed reader with barriers for ordering tests and at least one actual slow or remote-mounted volume for release evaluation. Record OS/filesystem, hardware, display refresh, build, fixture, cache state, sample count and median/tail. Separate cold, OS-warm and application-cache hits. Use isolated fixtures for cold tests. Use syscall tracing on Linux or platform equivalents in separate runs. A frame-ready event is an engine metric until the UI consumes and draws it.

**Working targets to validate on reference hardware.** For a warm 100k local directory, aim for input/loading feedback by the next frame and first usable rows within 100 ms. Aim for p95 foreground work below one 60 Hz frame (16.7 ms) while scanning, typing and scrolling. For slow storage measure first rows relative to the first successful read, plus input and repaint latency while the read is blocked. Record final completion and peak RSS alongside latency. Use repeated runs for percentiles and deterministic work-count assertions in CI.

### 2. Remove whole-directory work from steady frames — P0, after 1

**Phase 1 status — implemented and measured.** Cursor steps, reveal, Quick View, footer availability and status use maintained view state. Byte totals and export order are covered by tests, including refresh and deletion. [Task 2 checkpoint](performance-phase1-results.md#steady-frames-and-export).

**Files and implementation.** In engine `lib.rs`, add a cheap validated `has_operands` and maintain current visible position plus selected file byte total. Update on all mark commands, selection ranges, refresh/size changes, filter, reorder, navigation and error. Paths remain the canonical targets. Rebuild transient positions once per new view, prefer a cached cursor index to a second path map until lookups justify it. In UI `lib.rs` and `panes.rs`, use these queries in footer, status, Quick View and reveal. In `dialogs.rs` materialize operands only in branches that consume them. Iterate visible entries directly for export-all and use marked membership for a subset, retaining output order.

**Acceptance and tests.** A stationary frame and one ordinary cursor step visit O(viewport) rows or fewer, including a cursor at the end and all rows marked. Drawing the footer clones zero operand paths. Check byte totals against full recomputation after all selection modes, filtering and refresh. Compare exported text/order and drag operands before/after. Benchmark head/middle/end, no marks and 100k marks, with the footer enabled. Measure large exports separately from steady scrolling.

### 3. Bound listing work and cancel stale producers — P0, after 1

**Phase 2 status — implemented and measured.** Two listing workers, two replaceable visible-pane requests, cooperative cancellation, and bounded ready results are in place. Archive reads use the existing archive cancellation control. A Linux FIFO and gated stress tests cover obsolete reads and worker bounds. A blocked syscall can still hold a slot until the OS returns. [Phase 2 results](performance-phase2-results.md).

**Files and implementation.** In engine `lib.rs` (`start_scans`, navigation/scope changes, tab lifecycle, `poll`, Drop) and `listing.rs`, replace spawn-per-scan with a small fixed blocking worker set. Start with two listing slots and one replaceable pending foreground listing per visible pane. Use tab IDs rather than pane positions for delivery. Check cancellation before entering directories, between entries, before metadata/comments and before result publication. Handle tab close, reset, swap, duplicate removal and workspace restore. Keep queued/held mutation jobs under their existing explicit controls. Coalesce scan wakes and use bounded delivery with cancellation-aware backpressure. The UI must never wait for a sender or join a worker blocked in filesystem I/O. Keep terminal errors/completions and conflict decisions reliable.

**Acceptance and tests.** Inject blocked A, fast B, then A again with distinct generations. Close/move a tab mid-scan and restore tabs with a result pending. Assert stale rows, errors and completion flags are ignored. Stress 100 requests while the consumer is paused. Assert configured worker/mailbox bounds and release of stale buffers after workers reach a cancellation point. Verify the other pane and file-operation conflicts still progress when one slot is blocked. Measure backlog and time from supersession to last obsolete metadata attempt. If both slots block, keep UI feedback immediate and retain only the latest pending work.

### 4. Make navigation validation asynchronous — P0, after 3

**Phase 2 status — implemented and tested.** Path and history validation use a separate bounded pool. The current view remains available during validation, and the UI checks tab, request, peer and focus revisions before applying results. Explicit background opens are independently keyed. Pending foreground work is canceled when switching away from its tab. Native slow-mount latency remains to be measured. [Phase 2 results](performance-phase2-results.md).

**Files and implementation.** Split engine `navigate`/`history` into pure intent construction, worker validation/canonicalization and UI-thread commit. Capture origin tab, base, intended history index, lock/new-tab/background intent, linked-peer identity and a monotonically increasing request ID **before** dispatch. Show a pending destination promptly. Keep the previous committed directory, operands and history until validation succeeds. Resolve relative paths against their captured base. Check request and tab state before committing location, history and active focus. Separate independent explicit background-tab opens from replaceable same-tab intents. Linked follow-up must never overwrite a newer peer navigation. Preserve existing behavior for valid but unreadable directories whose subsequent listing fails.

**Acceptance and tests.** Delayed or failed validation preserves navigation and correct error reporting. Simulate reordered success/failure, Back/Forward, Parent, a tab switch during validation, locked and reset tabs, explicit background opens and paired bookmarks. Assert no late focus steal, duplicate history entry or synchronous path probe during dispatch. Time command return and input in the opposite pane with validation held behind a barrier.

### 5. Move ancillary probes off the frame path — P0, after 1 and 3

**Phase 2 status — implemented and tested on Linux.** Space, places, tree, and dialog reads run independently of listing and validation. CLI validation starts with the app active. Native pickers, unmount and clipboard retain their threading. Windows and macOS validation and actual slow-mount release checks remain open. Whole-list sorting and projection on poll remain dependencies for Task 7. [Phase 2 results](performance-phase2-results.md).

**Files and implementation.** In UI `lib.rs` (`App::new/content/logic`), `panes::tree`, desktop `main.rs` and engine `space/tree_folders`, issue keyed, coalesced background requests for places, free space and expanded tree nodes. Keep the last value during refresh and briefly cache failures. Store tree children by shared handle. Preserve depth/display limits and tree symlink policy. Separate platform enumeration from the non-Send desktop clipboard/dialog adapter. Bound ancillary work independently so a stuck drive probe cannot consume all navigation slots. As a second patch, move CLI startup validation, list imports, properties, numbered-part searches and dialog destination checks onto the same bounded read path, keyed to the originating tab/dialog. Keep native picker presentation on its required thread.

**Acceptance and tests.** A delayed or offline drive must allow an initial window, navigation and uninterrupted repaint. Repeated frames on a failed space lookup generate at most one pending request per key and respect retry delay. Switch directory or close the dialog mid-probe and verify late results are ignored. Count directory reads with many expanded nodes. Exercise Linux mounts, macOS volumes and Windows drive/UNC failures or run native smoke tests where available.

### 6. Remove redundant work within a single scan and projection — P0, after 1

**Phase 1 status — implemented and measured.** Ordinary scans stream entries, sorts borrow per-row keys and filters build visible indices directly with compiled criteria. Frozen-sort parity, recursive exclusion, duplicate paths, links and native Unix path identity passed on Linux. The Windows attribute test requires a Windows run. [Scan and projection measurements](performance-phase1-results.md#results).

**Files and implementation.** In engine `listing.rs`, process ordinary `ReadDir` entries as they arrive. Pass enumeration metadata when it has the same link semantics. Keep path-based fallback for virtual lists and retain deduplication for overlapping roots/lists. Use one comment map for the ordinary directory and allocate a parent key only on a miss in multi-parent scans. Compile matching criteria once per change. An empty text needs no per-name normalization, while file/dir/read-only, hidden, ignore and recursive ancestor constraints still apply. Build visible indices directly and reconcile only actual marks. For natural and insensitive sorts, derive lowercase names once per row used by a sort and compare borrowed keys. Preserve ordered sort columns, leading-zero behavior and final path tie-break.

**Acceptance and tests.** Compare the complete output with a frozen reference for every sort column and direction, equal keys, Unicode case/accents, glob masks including `*.*`, mixed file/dir flags, duplicate list paths, nested ignored folders, inaccessible paths and broken links. Test Windows hidden/system attributes and Unix non-UTF-8 path identity. Count duplicate-path allocations, comment opens and normalizations. Benchmark scan and preparation separately on 100k random names. Retain key storage across actions only if the measured benefit justifies the bytes.

### 7. Publish an immutable listing and a versioned view — P0, after 2, 3 and 6

**Files and implementation.** In engine `lib.rs` and `listing.rs`, separate owned raw entries (shareable, e.g. `Arc<[Entry]>`) from per-tab ordered visible indices. Build the sorted/filtered view and path-to-position information needed for reconciliation on a bounded worker. Apply one ready view in `poll`. Distinguish raw listing generation from view revision (sort, hidden/ignore, recursive scope, filter). A settings change invalidates inactive views too. Coalesce successive filter edits, preserve invalid-mask feedback and keep selection changes made during preparation. Route sort preference edits in UI `settings.rs` to reproject resident data. Audit `Tab::operands` and all direct `entries` callers so ordered commands retain the old sorted order. Handle destruction of superseded large snapshots on a worker if install/drop instrumentation exceeds the frame budget.

**Acceptance and tests.** Change sort/filter during enumeration, switch to an inactive tab after a global option edit, and mark rows between submit and commit. Only the latest compatible view can install. Test recursive scope transitions in both directions and masked finds/marks. A sort-only edit produces zero directory reads. Benchmark poll/install with 100k marks as well as zero marks. If pruning marks alone exceeds budget, prepare against a selection revision and reconcile subsequent edits before commit. Measure peak overlap of old/new data and bounded stale result retention.

### 8. Publish a usable first page before completion — P0, after 4 and 7

**Files and implementation.** Extend `listing::scan`, engine events and UI `panes::empty/rows/gallery/panel_status` with partial and final states. Ship for ordinary directories first. A simple first increment publishes one bounded, sorted provisional page of eligible, fully formed entries and then the complete prepared view. Collect on the worker in one pass, flush the first page on count or elapsed time between reads (try 64 eligible entries or 16 ms, then tune). Emit discovered count at a coalesced cadence if needed. Avoid cloning or sorting every prefix. For refresh, keep the previous complete view until replacement. Recursive exclusion may require ancestor facts, so retain the complete-result path for virtual/recursive views until parity tests pass.

**Interaction contract.** Label partial counts/loading explicitly. Bind actions and scroll anchors to native paths and the listing generation, including pointer-down versus pointer-up across reorder. Keep a user's focused path on final sort. If no user interacted, apply normal first-row focus on completion. Enable opening or marking known rows. For commands requiring the full universe (mark all, invert, range over undiscovered rows, find/export-all), defer with visible feedback until the same generation completes, or disable them with a loading explanation. Discard deferred commands when superseded. Keep root errors, empty directories, skips and final completion distinct.

**Acceptance and tests.** Gate the producer after its first eligible batch and verify a row draws, can be opened, and navigation away succeeds before releasing the gate. Test no matches, late matches, links, an error after a partial result, input during final reorder and sort/filter revision changes. The final ordered rows, metadata and skipped count must match the reference. Measure input-to-first-draw versus time to full completion, total sort calls, buffer high-water marks and p95 frame time. Add intermediate pages only if scrolling past the first page while loading is a measured need.

### 9. Share recent ordinary directory listings — P1, after 7–8

**Files and implementation.** In engine `lib.rs` add a small in-memory cache of completed ordinary-directory snapshots keyed by resolved native path and scan scope. Share the raw snapshot and coalesce in-flight requests from both panes. Detaching a tab cancels a scan only when its last subscriber leaves. Keep cursor, filter, sorted view, marks and history local to each tab. A cached raw listing still requires a projection. Retain the last compatible ready view for fast first paint when its view options match exactly. On a known history hit, allow immediate provisional display under its cached identity while validation runs. Bind commands to the committed location, and withdraw a rejected provisional view. Mark stale data as refreshing. Explicit refresh always validates. Exclude flat, recursive and arbitrary lists from cross-location reuse initially.

**Memory and freshness.** Use a byte-weighted LRU with an entry-count cap. Charge owned path/string capacities, indices and shared snapshots once. Limit inactive-tab strong references too, or cache eviction cannot reclaim memory. Preserve inactive tab state if its data must be reloaded. Active listings larger than the cache must remain usable and bypass retention. Keep cached data in memory only. Track age, dirty revision, and last validation. Use conservative age-based background revalidation until watch coverage is established. A directory's mtime alone cannot validate changes to child contents, permissions or link targets.

**Acceptance and tests.** Two panes visiting the same folder produce one scan and independent sorting/marks. A→B→A displays matching cached rows before delayed revalidation. Change/delete the target, revisit after expiry, and check errors plus removal of stale operands. Many large tabs and one oversized directory exercise eviction and pinned bytes. Compare first cached paint, scan count and RSS after repeated evictions.

### 10. Narrow refresh to affected locations — P1, after 9

**Files and implementation.** In engine `operations.rs` and `lib.rs` derive a conservative set of affected parent directories/roots for each job, or accumulate actual touched paths while it runs. Carry effects through success, partial failure and cancellation. Include source and destination of moves, sidecar comments, recursive properties, split/join outputs and generated manifests. Verify, statistics and in-memory hashing benchmarks should not dirty directory state merely on completion. For recursive/list tabs, invalidate on intersecting roots or list members/parents, falling back to dirty when scope is uncertain. Keep manual Refresh authoritative across tabs. Coalesce dirty notifications during a scan into at most one outstanding follow-up per revision. Schedule fallback refresh intervals from completion to avoid permanent scanning on slow storage.

**Acceptance and tests.** Verify a read-only job causes zero listing scans, rename/move update both affected panes, partial copy dirties everything touched, inactive tabs pick up changes when reopened and unrelated directories remain cached. Test auto-refresh off, manual refresh, stale jobs overlapping a newer navigation and missed external changes in fallback mode. Count scans per job and idle I/O over multiple current four-second intervals.

### 11. Use native watch notifications as invalidation hints — P1, after 9–10

**Files and implementation.** Add a thin engine watch adapter and an optional dependency in the engine manifest if required. Watch active ordinary directories nonrecursively with shared subscriptions by path. Register before baseline enumeration and record changes received during that scan. Debounce a burst into one dirty revision. On overflow, backend error, mount disappearance or notification ambiguity, reconcile with a full scan. Bound ingress by coalescing into a dirty flag when full. Release watches on navigation/close. Preserve explicit refresh and the auto-refresh toggle. For unwatched lists and unsupported/unreliable mounts use bounded adaptive polling. Keep eventual revalidation for dropped notifications, moves outside coverage and changes to symlink targets. Preserve current manual/job refresh behavior for recursive and flat modes.

**Acceptance and tests.** Fake an event during initial scan, overflow, duplicate events, a notification after unsubscribe and a directory replaced at its original name. Eventually converge to an independent listing. Ordinary idle watched directories should cease the four-second scan cycle. Compare idle scan count and time to visible change on local Linux/macOS/Windows plus a mount with watch support absent. Land this invalidation-only adapter before adding row-level edits.

### 12. Apply small changes incrementally — P1, after 11

**Files and implementation.** In the watch adapter, `listing.rs` and engine cache/view handling, coalesce create/modify/remove by native name and re-read only affected entries on a worker. Pair renames only when reliable, otherwise reconcile both parents. Treat `descript.ion` changes as invalidating the directory's comments. Publish a revision-consistent patch to each subscribed tab. Batch view edits, maintain sort, filter, mark/cursor and selected-byte invariants. Account for O(N) index shifts or snapshot copying even when metadata I/O is O(changes). Start with worker-side index rebuilds if they meet the measured budget. When a burst exceeds a measured threshold or differs from the patch's base revision, request a full reconcile.

**Acceptance and tests.** Replay reordered and duplicate events, same-name replacement, metadata-only resort, deletion of focused/marked files, cross-directory rename and sidecar rewrite. Compare with a fresh scan after quiescence. One ordinary file edit should read metadata for O(1) paths. Benchmark one edit and a 10k-file burst in 100k entries, tracking CPU, bytes copied, convergence time and rescans.

### 13. Defer expensive metadata only when measurements warrant it — P2, after 6–8

**Files and implementation.** In engine `listing.rs/lib.rs` and UI `panes.rs/dialogs.rs`, prototype basic rows from enumeration plus explicitly unknown optional fields. Reuse metadata already cheaply available on the native backend. Default Details shows size and modified time, while Compact often needs only names and type. Prioritize visible rows and resolve type, hidden/system status, link-to-directory behavior and any fields required for inclusion or definitive sort. Batch metadata by directory and view revision. Unknown values require a placeholder. Never interpret them as zero, writable or a file. Full-column sorting and bulk export must await the necessary data. Properties and destructive operations must retain their own validation against current filesystem state.

**Acceptance and tests.** Compare eager and lazy modes on local and latency-injected storage in Compact and Details, both name- and size-sorted. Count metadata requests, first usable rows, final-order time, unknown-field dwell and peak bytes. Test broken links, permissions failure, timestamp absence, Windows attributes and non-UTF-8 names. Proceed only if foreground work/latency improves for the intended workloads without unacceptable final-view or memory regression.

### 14. Discard stale previews, then evaluate bounded prefetch — P2, after 3 and 8 for previews, 9 for directory prefetch

**Files and implementation.** In UI `Previews::{get,poll}`, `panes::gallery/show_preview` and engine `preview`, track the current visible demand set per pane/view. Remove obsolete queued requests, prioritize Quick View, discard superseded results before texture creation, and cap pending decoded bytes and upload work per frame. Preserve display-size keys, decoder limits and nonblocking submission. Invalidate on known file changes even with coarse mtimes. Let an in-progress decode reach a safe boundary. First ship this change without speculative reads.

As a separate experiment, allow one idle low-priority listing for a focused directory after a dwell interval. Skip already cached, in-flight or unreliable/slow locations and yield to either pane's foreground requests. Reuse task 9's cache budget. If a blocked speculative call can occupy the last foreground slot, do not start it. Measure the actual likelihood of entering a focused folder before making prefetch a default.

**Acceptance and tests.** Race rapid Gallery scroll and Quick View changes with late decodes. Assert irrelevant results do not upload, queues stay within byte/count caps and foreground reads take priority. Trace decode starts vs displayed previews, GPU upload time, hit rate, discarded bytes and time to the latest preview. A/B directory prefetch on repeated keyboard traversal and on a slow mount. Leave it off if I/O or tail latency grows without a reproducible navigation benefit.

## Compatibility and completion

Keep engine inputs, immutable results, cancellation and invalidation expressed in plain Rust types. This leaves a future plugin provider able to supply batches, optional metadata and change hints through the same bounded interface. Define a provider-specific cache identity only when a second provider exists. Avoid persisting transient generations, cached rows or worker configuration in saved tabs. Local operations must retain native path identity and their existing collision, link and cancellation checks.

For each increment, run `cargo test --workspace`, including the existing navigation/mark restoration and recursive-filter workflow tests. Add deterministic interleaving tests at the engine boundary and run the release fixture for the affected scenarios. Before rollout, exercise both panes in Details, Compact, Gallery and Quick View, including tab locks, restored workspaces, linked navigation, operations and fresh/failed refresh. Publish the before/after timings, counts, fixture and any platform gaps. A change earns its place when the first usable view arrives sooner or less unnecessary work occurs, while final contents and command targets remain correct.
